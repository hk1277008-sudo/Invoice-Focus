# INVOICEFOCUS — FULLY FUNCTIONAL DOCUMENT TYPES & PROFESSIONAL TEMPLATE SYSTEM

You are continuing work on the existing InvoiceFocus application.

This is a focused implementation task.

The current problem is that when users select different invoice templates/designs, the generated documents appear identical. Selecting a different template does not produce a genuinely different visual design.

This must be fixed properly.

Follow the existing InvoiceFocus project Skill and all existing project rules.

Do not redesign unrelated pages.

Do not modify unrelated functionality.

Do not create fake template selection.

Do not simply change template names while keeping the same underlying design.

The selected document type and selected visual template must genuinely affect the generated document and PDF output.

---

# PRIMARY OBJECTIVE

Build a genuinely functional document type and template system.

The system must distinguish between:

1. **Document Type**
2. **Visual Design Template**

These are separate concepts and should be implemented accordingly.

The user's selection must be persisted and respected when generating the final document/PDF.

---

# 1. DOCUMENT TYPES

Support the document types that are already intended or exposed by the existing application.

At minimum, evaluate and implement these document types if they are currently part of the product scope:

* Invoice
* Receipt
* Estimate
* Quote

Do not automatically add additional document types beyond the existing intended product scope unless explicitly requested.

Each document type must have a meaningful purpose and appropriate terminology.

---

## INVOICE

The Invoice document should include appropriate invoice information such as:

* Business information
* Client information
* Invoice number
* Issue date
* Due date
* Line items
* Quantity
* Unit price
* Subtotal
* Discount where supported
* Tax where supported
* Total
* Notes
* Payment information where supported

The final output must clearly look like an invoice.

---

## RECEIPT

The Receipt document should clearly communicate that payment has been received.

Use appropriate terminology and fields such as:

* Receipt number
* Business information
* Customer/client information
* Payment date
* Payment method where supported
* Reference to the original invoice where applicable
* Paid items
* Amount paid
* Total paid
* Notes where applicable

Do not simply rename an Invoice to "Receipt."

The visual hierarchy and terminology must communicate that it is a receipt.

---

## ESTIMATE

The Estimate document should clearly communicate that it is an estimated cost and not a final invoice.

Use appropriate terminology such as:

* Estimate number
* Estimate date
* Expiration date where supported
* Business information
* Client information
* Estimated line items
* Estimated subtotal
* Estimated tax
* Estimated total
* Notes
* Terms where supported

The final output must clearly look like an estimate.

---

## QUOTE

The Quote document should clearly communicate that it is a formal quotation or proposal for a customer.

Use appropriate terminology such as:

* Quote number
* Quote date
* Valid until
* Business information
* Client information
* Quoted items
* Subtotal
* Discount where supported
* Tax where supported
* Quoted total
* Terms
* Notes

The final output must clearly look like a quote.

Do not simply rename an Invoice to "Quote."

---

# 2. VISUAL DESIGN TEMPLATES

The application should support genuinely different visual designs.

At minimum, implement or correctly connect these visual design categories if they are already part of the existing product:

### Minimal

Design characteristics:

* Clean
* Large whitespace
* Minimal borders
* Simple typography
* Strong hierarchy
* Few decorative elements
* Highly readable
* Modern and understated

The design should feel lightweight and elegant.

---

### Professional

Design characteristics:

* Polished business appearance
* Clear section hierarchy
* Balanced spacing
* Strong but restrained branding
* Professional table structure
* Clear totals section
* Suitable for freelancers, consultants, and agencies

The design should feel more structured than Minimal.

---

### Enterprise

Design characteristics:

* Structured corporate layout
* More detailed information hierarchy
* Strong section separation
* More comprehensive business information
* Clear document metadata
* Detailed totals and terms areas
* Suitable for larger businesses and corporate clients

The design should feel more formal and information-dense than Minimal and Professional.

---

# 3. TEMPLATES MUST ACTUALLY BE DIFFERENT

This is critical.

If a user selects:

* Minimal
* Professional
* Enterprise

the generated document must visibly change.

Do not create three template names that all render the same layout.

The differences should include meaningful changes such as:

* Typography
* Spacing
* Header structure
* Logo placement
* Table styling
* Section hierarchy
* Borders
* Totals presentation
* Business information placement
* Footer structure
* Terms and notes layout

The differences must be visible in both:

1. The document preview
2. The generated PDF

Document Type:

`Minimal`

Document Type:

`Invoice`

Visual Template:

`Professional`

or:

Document Type:

`Estimate`

Visual Template:

`Enterprise`

The selected combination must determine the final document output.

For example:

* Invoice + Minimal
* Invoice + Professional
* Invoice + Enterprise
* Receipt + Minimal
* Receipt + Professional
* Receipt + Enterprise
* Estimate + Minimal
* Estimate + Professional
* Estimate + Enterprise
* Quote + Minimal
* Quote + Professional
* Quote + Enterprise

Do not create unnecessary duplicate code for every combination.

* Document type controls content and terminology.
* Template controls visual presentation.

# 5. TEMPLATE SELECTION MUST PERSIST

When a user selects a template:

* Save the selected template with the document/invoice data where appropriate.
* Reloading the document must preserve the selected template.
* Editing the document must preserve the selected template.
* Duplicating a document should handle the template correctly.
* PDF generation must use the saved template.
* Preview must use the selected template.

Do not rely only on temporary frontend state.

---

* Do not use fake preview cards.
* Selecting a template must actually apply it.

If preview images or preview components are used, they should accurately represent the generated output.
